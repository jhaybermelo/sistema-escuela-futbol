# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A management system for "Escuela de Fútbol Yiverth Estrella" (a Colombian football school): student registration with auto-assigned age categories, a monthly-fee billing engine with mid-cycle proration, payment tracking with an official branded receipt template (shareable via WhatsApp), carnet (ID card) generation, and email/WhatsApp payment reminders. Built as `backend/` (FastAPI) + `frontend/` (React), following the architecture of a sibling reference project (`SistemaFacturacion`).

## Commands

### Local development (fastest iteration)
```bash
# Backend needs Postgres — run it via Docker even for local dev (see Docker networking gotcha below)
docker compose up -d postgres-db backend

# Frontend with hot reload
cd frontend && npm run dev          # http://localhost:5173, proxies /api to backend:8000
```

### Full stack via Docker Compose
```bash
docker compose up -d --build        # dev: postgres + backend (--reload) + frontend (nginx) on :80
docker compose up -d --build <service>   # rebuild just one service, e.g. `frontend` or `backend`
```
Production deploy uses `docker-compose.prod.yml` instead (adds Caddy for automatic HTTPS, drops host port bindings on postgres/backend — see that file's comments).

### Database migrations (run inside the backend container)
```bash
docker exec escuela-futbol-backend alembic revision --autogenerate -m "description"
docker exec escuela-futbol-backend alembic upgrade head
```
**Always inspect autogenerated migrations before applying.** Adding a `NOT NULL` (and/or `UNIQUE`) column to a table that already has rows fails without a `server_default` — this has come up repeatedly (e.g. `server_default=''` for text snapshot columns, `server_default=sa.text('gen_random_uuid()::text')` for unique token columns, since a fixed literal default would violate uniqueness).

### Seed admin user
```bash
docker exec escuela-futbol-backend python -m scripts.seed_admin
# admin@escuela.com / admin123 (override via SEED_ADMIN_EMAIL / SEED_ADMIN_PASSWORD env vars)
```

### Frontend checks (no backend test suite exists)
```bash
cd frontend
npx tsc -b --noEmit    # typecheck
npx eslint src         # lint
npm run build          # production build (also typechecks)
```
There is no automated backend test suite (pytest is not installed) or frontend test runner — verification has been done by curling the running API directly and checking `docker logs escuela-futbol-backend` after every change.

## Critical environment gotcha: Docker Desktop networking on this machine

Host→container connections to `127.0.0.1:<published-port>` are unreliable on this Windows/Docker Desktop setup — asyncpg handshakes to Postgres fail outright, and stale `docker-proxy` processes on `127.0.0.1` have served old responses after a container rebuild. **Always use `localhost` instead of `127.0.0.1`** when curling the API from the host or configuring `vite.config.ts`'s dev proxy target — `localhost` resolves to the IPv6 loopback listener, which does not have this problem. Container-to-container traffic (e.g., frontend's nginx proxying to `escuela-futbol-backend:8000`, or backend to `postgres-db:5432`) is unaffected and always reliable — prefer running things through Docker over bare `uvicorn`/host networking when a real Postgres connection is needed.

## Backend architecture (`backend/app/`)

Strict layering, one file per resource per layer:
- `models/` — SQLAlchemy 2.0 async ORM (`Mapped`/`mapped_column`), re-exported from `models/__init__.py` (also alembic's autodiscovery entrypoint via `from app.models import *` in `alembic/env.py`).
- `schemas/` — Pydantic v2: `*Create`/`*Update` (all-optional)/`*Response` (`from_attributes=True`)/`*ListResponse{items,total,page,size,pages}`.
- `repositories/` — one class per aggregate, takes `db: AsyncSession` in `__init__`, owns all `select()`/filter/paginate logic, **never commits** (caller commits).
- `services/` — only for real cross-entity business logic with its own transaction (`BillingService`, `ReminderService`, `CategoriaAssignmentService`, `carnet_service`, `notification_service`, `recibo_service`). Simple CRUD skips this layer — router calls the repository directly and commits itself.
- `routers/` — one `APIRouter` per resource, mounted under `/api` in `main.py`. Role gating is via `dependencies=[Depends(require_admin)]` at the router level (whole resource is admin-only) or per-route.
- `core/` — `security.py` (JWT + bcrypt), `dependencies.py` (`get_current_user`, `require_admin`), `logging_config.py` (per-domain rotating logs via `get_logger(domain, settings.LOG_DIR)`), `scheduler.py` (APScheduler), `date_utils.py`.

**Gotcha**: a repository method named `list` that returns `tuple[list[X], int]` will break if the class defines other methods *after* it with `list[...]` in their return-type annotation — Python resolves `list` inside the class-body namespace to the just-defined `list` *method*, not the builtin, causing `TypeError: 'function' object is not subscriptable` at class-definition time. Fix: add `from __future__ import annotations` at the top of any new repository file (already done in `mensualidad_repository.py`, `alumno_repository.py`, `pago_repository.py`).

**Async relationship loading**: SQLAlchemy async cannot lazy-load relationships implicitly. Every relationship accessed after the initial query must be eager-loaded via `selectinload()` (nested: `selectinload(Mensualidad.alumno).selectinload(Alumno.categoria)`), or you get a `MissingGreenlet` error.

**Session identity-map staleness**: within a single request, a bulk `delete()`/raw update executed via `db.execute()` does not refresh already-loaded ORM relationship collections on objects already in the session. `marcar_pagado`/`marcar_pendiente` in `routers/mensualidades.py` work around this by re-fetching `total_pagado` via a fresh aggregate query rather than trusting `mensualidad.pagos` after mutating pagos in the same request.

### Billing engine (`services/billing_service.py`) — the core domain logic

- `_periodo_actual(dia_corte, hoy)`: the (periodo_inicio, periodo_fin) cycle containing a date, given the school's fixed monthly cutoff day (`SchoolConfig.dia_corte`).
- `_periodos_en_rango(dia_corte, desde, hasta)`: list of consecutive periods between two dates.
- `generar_historial_alumno(alumno, config, hasta=None)`: generates **all** missing `Mensualidad` rows for a student from `max(SchoolConfig.fecha_inicio, alumno.fecha_ingreso)` through today (or `hasta`) — not just the current period. Only the first period is prorated (if the start date falls mid-cycle, using the student's category's `dias_entrenamiento` to compute a day-count ratio); idempotent via the `(alumno_id, periodo_inicio)` unique constraint on `Mensualidad`.
- `generar_historial_todos(config)`: runs the above for every active student. This is what both the `/mensualidades/generar-periodo` button and the daily scheduler job call — there is no separate "just the current period" code path anymore; a single idempotent full-backfill call handles new periods, catch-up after downtime, and manually-created historical gaps uniformly.
- Called from `routers/alumnos.py`'s `create_alumno` **after** the category has been resolved and flushed (proration needs `alumno.categoria.dias_entrenamiento`) — category-resolve → flush → `generar_historial_alumno` → single commit is a deliberate ordering contract, not incidental.

### Receipts (`Pago` model + `services/recibo_service.py`)

Each `Pago` **snapshots** `alumno_nombre`, `categoria_nombre`, `acudiente_nombre`, `acudiente_telefono`, `periodo_texto`, and `conceptos` (JSONB) at creation time, so a receipt never changes retroactively if the student's profile is edited later. `recibo_tipo` is `generado` (rendered live from stored data, no PDF file on disk — see `frontend/src/pages/ReciboPage.tsx` / `ReciboView.tsx`), `subido` (a physical receipt file uploaded to `/uploads/recibos/`), or `historico` (created by the "marcar pagado" quick-toggle for backfilled months, no receipt file). Every `Pago` has a random `token` (UUID) used for the unauthenticated public share link at `/r/:token` → `GET /api/public/recibos/{token}` (`routers/public.py`, no `require_admin`) — this is the only intentionally-unauthenticated API route; do not add auth to it (it's how guardians view/print receipts without a system account) but also do not widen what it exposes.

### Scheduler (`core/scheduler.py`)

APScheduler `AsyncIOScheduler`, in-process, single backend instance assumed (do not run the backend with multiple workers/replicas — jobs would double-fire; see the comment in `docker-compose.prod.yml`'s backend `command:`). Two daily cron jobs: billing (`generar_historial_todos` + `marcar_vencidas`) and reminders (`ReminderService.enviar_recordatorios`, dedup'd via the `(mensualidad_id, tipo, canal)` unique constraint on `NotificationLog`).

### Role scoping

`Usuario.rol` is `"admin"` or `"entrenador"`. Coaches are optionally scoped to categories via the `entrenador_categoria` association table; a coach with **no** categories assigned sees all students (non-financial fields only) rather than none. Financial resources (`mensualidades`, `pagos`, `notificaciones`, `usuarios`, `config`) are admin-only via router-level `require_admin`. The scoping check (`_scope_categorias`) is duplicated locally in `routers/alumnos.py` and `routers/dashboard.py` rather than shared — intentionally small enough not to warrant an abstraction.

## Frontend architecture (`frontend/src/`)

Flat convention, no feature folders: `api/*.ts` (one per backend resource, thin axios wrappers, exported as plain async functions), `pages/*.tsx` (one per route, lazy-loaded in `App.tsx`), `components/` (`Layout.tsx`, `ProtectedRoute.tsx`, `ui/` primitives, a few shared modals like `PagoFormModal.tsx` and `ReciboView.tsx`), `context/AuthContext.tsx`, `types/index.ts`.

- `api/client.ts`: single axios instance, request interceptor attaches `Authorization: Bearer <token>` from `localStorage` if present, response interceptor redirects to `/login` on 401.
- Routing (`App.tsx`): most routes are nested under a `ProtectedRoute` + `Layout` wrapper; admin-only pages additionally wrap themselves in a second `<ProtectedRoute requireAdmin>`. Two routes are deliberately **outside** `Layout`/auth: `/login` and `/r/:token` (public receipt view). `/recibos/:pagoId` (the admin receipt view) is outside `Layout` (full-page, print-friendly) but still behind `ProtectedRoute requireAdmin`.
- Route ordering matters for static-vs-dynamic segments, e.g. `/alumnos/nuevo` must be registered before `/alumnos/:id`.
- `ReciboView.tsx` is a pure presentational component (shared CSS in `ReciboPage.css`, a faithful port of the club's official HTML/CSS receipt design — do not restructure its class names without checking print output) reused by both the authenticated `ReciboPage.tsx` and public `ReciboPublicoPage.tsx`.
- A recurring ESLint finding (`react-hooks/set-state-in-effect`) fires on the standard "populate controlled form state once an async query resolves" pattern (edit forms, blob-to-object-URL for the carnet image). This is treated as a known false positive in this codebase — silence it with a targeted `// eslint-disable-next-line react-hooks/set-state-in-effect` and a one-line comment, don't restructure the component to avoid it.

## Adding a new resource end-to-end

Follow the existing `alumnos` or `mensualidades` chain as the template: model → schema → repository → (service if cross-entity logic) → router (mounted in `main.py`) → alembic migration (generate inside the container, inspect it, apply it) → `api/<resource>.ts` → page component → route in `App.tsx`. Verify with real `curl` calls against the running container (with a valid JWT from `/api/auth/login`) before wiring the frontend — this has consistently caught bugs (route-ordering shadowing, missing eager-loads, migration defaults) earlier than testing through the UI.
